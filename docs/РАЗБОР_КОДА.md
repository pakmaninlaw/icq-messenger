Главное отличие от CRM: в CRM браузер **спрашивает**, а сервер **отвечает**. В мессенджере сервер должен **сам**
сообщить всем участникам, что кто-то написал сообщение. Для этого нужен другой способ связи.

### 1.3. WebSocket против обычного HTTP и long polling

> **Понятие. HTTP «запрос — ответ».** Обычный веб работает как переписка письмами: клиент пишет письмо (запрос),
> сервер отвечает, разговор окончен. Сервер **не может** написать первым — у него нет «обратного адреса», пока клиент
> сам не обратился.

Как тогда узнать о новом сообщении? Есть три способа:

| Способ | Как работает | Аналогия | Недостатки |
|---|---|---|---|
| **Опрос (polling)** | Клиент каждые N секунд спрашивает «есть новое?» | Каждые 5 минут звонить на почту: «мне ничего не пришло?» | Задержка до N секунд, масса пустых запросов |
| **Long polling** | Клиент спрашивает, а сервер «держит трубку», пока не появится новость (или не выйдет время ожидания). Получив ответ, клиент сразу спрашивает снова | Позвонить на почту и ждать на линии, пока оператор не скажет «пришло» | Каждое сообщение — новый HTTP-запрос со всеми заголовками; сервер держит много «висящих» запросов |
| **WebSocket** | Одно постоянное двустороннее соединение: после «рукопожатия» обе стороны пишут, когда хотят | Открытая телефонная линия или рация | Соединение нужно поддерживать; нужна поддержка на сервере и промежуточных серверах |

> **Понятие. WebSocket.** Протокол постоянного двустороннего канала поверх TCP. Начинается как обычный HTTP-запрос
> с просьбой «давай перейдём на WebSocket» (upgrade), а дальше по тому же соединению в обе стороны идут короткие
> сообщения без HTTP-заголовков. Задержка — доли секунды, накладные расходы минимальны.

> **Понятие. TCP/IP, адрес и порт.** IP-адрес — «адрес дома» компьютера в сети (`127.0.0.1` — этот же компьютер,
> `192.168.1.10` — компьютер в домашней сети). Порт — «номер квартиры»: какая программа на этом компьютере принимает
> соединение. Сервер ICQ слушает порт **5055**. TCP — протокол, который гарантирует доставку данных по порядку и без
> потерь; WebSocket работает поверх него.

### 1.4. Socket.IO: события, emit, broadcast

**Socket.IO** — библиотека поверх WebSocket, которая добавляет удобства:

- **Именованные события.** Вместо «просто сообщений» — события с именами: `join`, `message`, `typing`. Как письма
  с пометкой в теме «ЗАЯВЛЕНИЕ», «ЖАЛОБА»: получатель сразу знает, какому отделу передать.
- **`emit(имя, данные)`** — отправить событие. **`on(имя, функция)`** — «когда придёт событие с таким именем, вызови
  эту функцию».
- **`broadcast=True`** — разослать всем подключённым, а не только отправителю; `include_self=False` — всем, кроме
  самого отправителя.
- **`sid`** (session id) — номер конкретного соединения. У одного пользователя в двух вкладках — два разных `sid`.
- **Транспорты.** Socket.IO начинает связь через long polling (работает везде, даже через строгие прокси), а затем,
  если получается, «повышает» соединение до WebSocket. Настольный клиент прямо указывает оба транспорта:
  `transports=["polling", "websocket"]`.

Важно: Socket.IO — **свой протокол поверх WebSocket**. «Голый» WebSocket-клиент с Socket.IO-сервером договориться
не сможет — поэтому правила группы требуют именно библиотеку python-socketio.

### 1.5. Протокол обмена

Протокол описан в начале `server.py` и совместим с общим сервером группы:

| Направление | Событие | Данные | Смысл |
|---|---|---|---|
| клиент → сервер | `join` | `{login, password}` | Вход (первый вход с новым логином — регистрация) |
| клиент → сервер | `message` | `{text, time}` | Сообщение; `time` — «ЧЧ:ММ» |
| клиент → сервер | `typing` | — | «Я печатаю» (расширение) |
| сервер → клиент | `history` | `[message, …]` | Последние 50 сообщений — сразу после входа |
| сервер → клиент | `message` | `{nickname, text, time}` | Новое сообщение (всем) |
| сервер → клиент | `system` | `{text}` | Системное уведомление: «Добро пожаловать», «Анна в сети» |
| сервер → клиент | `error` | `{text}` | Ошибка: клиент показывает её и (как правило) возвращается ко входу |
| сервер → клиент | `users` | `[ник, …]` | Кто в сети (расширение) |
| сервер → клиент | `typing` | `{nickname}` | Кто-то печатает (расширение) |

Расширения `users` и `typing` «чужие» клиенты просто игнорируют — они не подписаны на эти события. Это пример
**обратной совместимости**: протокол расширен, не ломая существующих участников.

### 1.7. Путь одного действия: отправить сообщение

```
 Сергей (веб)             Сервер                                            Анна (настольный клиент)
    │ ввёл «Привет»,         │                                                    │
    │ Enter                  │                                                    │
    │ emit('message',        │                                                    │
    │  {text, time:"21:15"})►│ on_message:                                        │
    │                        │  1. кто это? online[sid] → «Сергей»                │
    │                        │  2. текст не пуст, не длиннее 1000                 │
    │                        │  3. антиспам: не больше 5 сообщений за 1 с         │
    │                        │  4. время в формате ЧЧ:ММ (иначе — серверное)      │
    │                        │  5. INSERT INTO messages … → icq.db                │
    │                        │  6. emit('message', {…}, broadcast=True)           │
    │ ◄═══ message ══════════│═══════════════════════════════════════════════════►│ фоновый поток socketio
    │ addMessage():          │                                                    │  кладёт событие в очередь
    │ своё — справа, зелёное │                                                    │ главный поток Tk (poll):
    │ (звука нет)            │                                                    │  handle → add_message
    │                        │                                                    │  + звук «о-оу»
```

Обратите внимание: отправитель **не рисует своё сообщение сам** в момент отправки — оно появляется у него, когда
сервер разошлёт его всем (включая отправителя). Так все участники видят сообщения в одном и том же порядке — в том,
в котором их принял сервер, — и отправитель видит, что сообщение действительно дошло.

### 1.8. ICQ и сайт портфолио

На витрине `C:\Projects\portfolio\portal.py` ICQ пока значится «в разработке» (`"status": "dev"`, `"url": None`) —
на общий сайт он не подключён. Но веб-клиент уже готов к этому: адрес Socket.IO строится как

## 2. server.py: сервер

### 2.1. Описание модуля

Docstring в начале файла — это **спецификация протокола** (таблица из раздела 1.5) и команда запуска

### 2.3. Настройки

```python
DB_FILE = os.environ.get("ICQ_DB") or os.path.join(BASE_DIR, "icq.db")   # путь к базе (тесты подменяют)
PORT = int(os.environ.get("ICQ_PORT", 5055))
HISTORY_SIZE = 50            # сколько последних сообщений отдаём при входе
MAX_TEXT = 1000              # максимальная длина сообщения
MAX_WRONG_PASSWORDS = 5      # после стольких ошибок подряд — бан
BAN_SECONDS = int(os.environ.get("ICQ_BAN_SECONDS", 15 * 60))   # длительность бана: 15 минут
SPAM_LIMIT = 5               # не больше 5 сообщений…
SPAM_WINDOW = 1.0            # …в секунду
LOGIN_RE = re.compile(r"^[A-Za-zА-Яа-яЁё0-9_.\-]{2,20}$")
TIME_RE = re.compile(r"^([01]\d|2[0-3]):[0-5]\d$")
```

> **Понятие. Переменная окружения.** Настройка, передаваемая программе снаружи при запуске. Тесты, например,
> ставят `ICQ_BAN_SECONDS=60` и временный `ICQ_DB`, не меняя код.

Разбор регулярных выражений (шаблонов проверки текста):

- `LOGIN_RE`: `^` — с начала; `[A-Za-zА-Яа-яЁё0-9_.\-]` — латинская или русская буква, цифра, `_`, `.`, `-`
  (буква «ё» указана отдельно, потому что в таблице символов она стоит вне диапазона `а-я`); `{2,20}` — от 2 до 20
  таких символов; `$` — до конца. Логины с пробелами, `<`, `>`, кавычками не пройдут.
- `TIME_RE`: часы — `[01]\d` (00–19) **или** `2[0-3]` (20–23), двоеточие, минуты — `[0-5]\d` (00–59).
  `25:99` и `bad` не пройдут.

Комментарий у `BAN_SECONDS` («у Ксении — 3 дня, у нас по умолчанию 15 минут») — ссылка на правила общего сервера
группы: там блокировка строже.

### 2.4. Приложение, Socket.IO и журнал

```python
app = Flask(__name__)
app.config["SECRET_KEY"] = os.environ.get("ICQ_SECRET") or os.urandom(16).hex()  # случайный ключ, если не задан
socketio = SocketIO(app, cors_allowed_origins="*", async_mode="threading")
logging.basicConfig(level=logging.INFO, format="%(asctime)s | %(levelname)-7s | %(message)s", datefmt="%H:%M:%S")
log = logging.getLogger("icq")
```

- `SECRET_KEY` — секрет для подписи данных сессий Flask. Здесь сессии не используются, но ключ задан по правилам
  хорошего тона; если он не указан снаружи, генерируется случайный при каждом запуске.
- `SocketIO(app, …)` — «надстройка» над Flask, добавляющая события реального времени.
- `cors_allowed_origins="*"` — разрешить подключение со страниц любых сайтов. **CORS** — правило браузеров «страница
  с сайта А не может без разрешения обращаться к сайту Б». Звёздочка снимает ограничение, чтобы подключались
  клиенты одногруппников с любых адресов. Удобно для учебного сервера, но это открытая дверь.
- `async_mode="threading"` — каждое соединение обслуживается в своём **потоке** (см. 2.5). Это самый простой режим,
  не требующий дополнительных библиотек вроде eventlet.
- `logging.basicConfig` — журнал в консоль с уровнями `INFO` (вход, выход) и `WARNING` (неверный пароль, бан, спам).

### 2.5. Состояние в памяти и «замок»

```python
lock = threading.Lock()
online = {}          # sid (номер соединения) -> логин
wrong = {}           # логин -> число неверных паролей подряд
banned = {}          # логин -> время окончания бана (unix time)
recent = {}          # sid -> очередь времён последних сообщений (антиспам)
```

Эти словари живут в оперативной памяти: быстро, но при перезапуске сервера обнуляются (все «выходят из сети», баны
снимаются). История и пользователи при этом сохраняются — они в базе.

> **Понятие. Поток (thread).** Поток — отдельный «исполнитель» внутри одной программы. В режиме `threading` каждый
> подключённый клиент обслуживается своим потоком, и они работают **одновременно**. Как несколько операторов
> колл-центра, которые параллельно принимают звонки.

> **Понятие. Гонка и блокировка (lock).** Если несколько операторов одновременно правят одну общую таблицу, возможна
> **гонка**: оба прочитали «неверных паролей: 4», оба прибавили 1 и оба записали «5» — одна попытка потерялась,
> и злоумышленник получил лишнюю попытку. **Замок** (`threading.Lock`) — как ключ от кабинета с журналом: взять
> журнал может только тот, у кого ключ; остальные ждут у двери. Конструкция `with lock:` берёт ключ в начале блока
> и гарантированно возвращает его в конце, даже при ошибке.

В коде под замок попадают только операции с общими словарями. Медленная работа (запрос к базе, проверка хеша) выполняется
**вне** замка — чтобы остальные потоки не стояли в очереди без нужды.

### 2.6. База данных: `db_connect`, `init_db`, `history`, `check_user`

```sql
CREATE TABLE IF NOT EXISTS users (
    login_key     TEXT PRIMARY KEY,   -- логин в нижнем регистре: по нему ищем и проверяем уникальность
    login         TEXT NOT NULL,      -- логин так, как его написал пользователь (для показа)
    password_hash TEXT NOT NULL,      -- НЕ пароль, а его хеш
    created_at    TEXT NOT NULL
);
CREATE TABLE IF NOT EXISTS messages (
    id       INTEGER PRIMARY KEY AUTOINCREMENT,      -- порядковый номер сообщения
    nickname TEXT NOT NULL,
    text     TEXT NOT NULL,
    time     TEXT NOT NULL,                          -- «ЧЧ:ММ», как прислал клиент
    ts       TEXT NOT NULL                           -- точная дата и время по серверу
);
```

- Ключ пользователя — **логин в нижнем регистре** (`login.casefold()` в Python): двух одинаковых логинов быть не может,
  и «Сергей» с «сергей» — один пользователь. Почему не средствами SQLite: встроенное сравнение `COLLATE NOCASE` не
  учитывает регистр только для латиницы, а кириллицу считает разными буквами. Поэтому нормализуем в Python и храним
  отдельно ключ и «красивое» написание.
- В `messages` два времени: `time` — «ЧЧ:ММ», как требует протокол для показа, и `ts` — полная отметка сервера для
  истории и разбора инцидентов.

**`history()`** — последние 50 сообщений в правильном порядке:

```python
rows = db.execute("SELECT nickname, text, time FROM messages ORDER BY id DESC LIMIT ?", (HISTORY_SIZE,)).fetchall()
#                                                       ↑ самые новые сначала, взять 50
return [dict(r) for r in reversed(rows)]                # развернуть: старые сверху, новые внизу — как в чате
```

Приём «взять N последних по убыванию и развернуть» — стандартный способ получить «хвост» списка.

**`check_user(login, password)`** — вход и регистрация одновременно:

```python
row = db.execute("SELECT password_hash FROM users WHERE login = ?", (login,)).fetchone()
if row is None:                                          # такого логина нет — регистрируем
    db.execute("INSERT INTO users (login, password_hash, created_at) VALUES (?, ?, ?)",
               (login, generate_password_hash(password), datetime.now().isoformat(timespec="seconds")))
    return "new"
return "ok" if check_password_hash(row["password_hash"], password) else "wrong"
```

Знаки `?` — параметры запроса: значения передаются отдельно от текста SQL, что защищает от **SQL-инъекций**
(подстановки команд в пользовательские данные). Конструкция `with db_connect() as db:` в Python-модуле `sqlite3`
означает **транзакцию**: по выходу из блока изменения фиксируются (`commit`), при ошибке — откатываются.

> **Понятие. Хеширование пароля.** Хранить пароли открытым текстом нельзя: утечка базы = утечка всех паролей (а люди
> используют один пароль везде). **Хеш** — «отпечаток пальца» пароля: по паролю отпечаток получить легко, а по
> отпечатку восстановить пароль практически невозможно. При входе сервер снимает отпечаток с введённого пароля и
> сравнивает с сохранённым. Два важных усиления: **соль** — случайная добавка, уникальная для каждого пользователя
> (одинаковые пароли дают разные хеши, заранее составленные «словари отпечатков» бесполезны); **медленный алгоритм** —
> вычисление одного хеша специально сделано затратным, чтобы перебор миллиардов вариантов занял годы.

`generate_password_hash` из Werkzeug делает всё это сам. В установленной версии Werkzeug 3.x по умолчанию используется
алгоритм **scrypt**, и хеш выглядит так: `scrypt:32768:8:1$<соль>$<хеш>` — в одной строке записаны алгоритм,
его параметры, соль и результат. (В старых версиях Werkzeug по умолчанию был PBKDF2 — тоже
надёжный «медленный» алгоритм.) `check_password_hash` читает из строки алгоритм и соль и
проверяет пароль.

**«Первый вход = регистрация»** — упрощение для учебного проекта: не нужна отдельная форма. Цена упрощения —
в разделе 9.

### 2.7. События Socket.IO

Функции с декоратором `@socketio.on("имя")` — обработчики событий, аналог маршрутов `@app.route` в обычном Flask.
Внутри обработчика `request.sid` — номер соединения, от которого пришло событие, а `emit(...)` без `broadcast`
отвечает **только этому** соединению.

**`users_online()`** — отсортированный без учёта регистра список уникальных логинов в сети (`set` убирает повторы,
если человек открыл две вкладки).

**`on_connect`** — просто запись в журнал «Подключение sid (IP-адрес)». Вход ещё не выполнен.

**`on_join(data)`** — вход:

```python
data = data if isinstance(data, dict) else {}           # защита: вдруг прислали не объект
login = str(data.get("login", "")).strip()
password = str(data.get("password", ""))
if not LOGIN_RE.match(login):
    return emit("error", {"text": "Логин: 2–20 символов — буквы, цифры, «_», «.», «-»"})
if not 1 <= len(password) <= 64:
    return emit("error", {"text": "Введите пароль (до 64 символов)"})
with lock:
    until = banned.get(login.lower(), 0)
    if until > time.time():                             # бан ещё действует — даже верный пароль не поможет
        return emit("error", {"text": f"Слишком много неверных паролей. Вход закрыт до {datetime.fromtimestamp(until):%H:%M}"})
result = check_user(login, password)                    # медленная проверка — вне замка
```

Дальше, снова под замком:

- `"wrong"` → счётчик `wrong[логин] + 1`; на пятой ошибке — `banned[логин] = сейчас + 15 минут`, счётчик
  сбрасывается, событие `error` «вход закрыт на 15 мин.»; иначе `error` «Неверный пароль (попытка n из 5)».
  В журнал — WARNING.
- `"ok"` или `"new"` → счётчик ошибок сбрасывается, `online[sid] = логин`.

После успешного входа — четыре отправки:

```python
emit("history", history())                                                      # новому: история
emit("system", {"text": "Добро пожаловать! Вы зарегистрированы." if result == "new"
                else f"С возвращением, {login}!"})                              # новому: приветствие
emit("system", {"text": f"{login} в сети"}, broadcast=True, include_self=False)  # всем, кроме него
emit("users", users, broadcast=True)                                            # всем: обновлённый список
```

Приём `return emit(...)` — «отправить ошибку и сразу выйти из функции»: так проверки идут подряд без вложенных
`if … else`. Все ключи блокировок — `login.lower()`, чтобы «Сергей» и «сергей» считались одним логином при подсчёте
ошибок.

**`on_message(data)`** — сообщение:

```python
login = online.get(request.sid)
if not login:
    return emit("error", {"text": "Сначала войдите (событие join)"})      # без входа писать нельзя
text = str(data.get("text", "")).strip()
if not text:
    return                                                                # пустые — молча игнорируем
if len(text) > MAX_TEXT:
    return emit("error", {"text": f"Сообщение длиннее {MAX_TEXT} символов"})
now = time.time()
with lock:
    q = recent.setdefault(request.sid, deque())    # очередь моментов последних сообщений этого соединения
    while q and now - q[0] > SPAM_WINDOW:
        q.popleft()                                # выбросить всё старше 1 секунды
    if len(q) >= SPAM_LIMIT:                       # за последнюю секунду уже 5 сообщений?
        return emit("error", {"text": "Не больше 5 сообщений в секунду — не спамьте"})
    q.append(now)                                  # записать текущее
```

> **Понятие. Скользящее окно (антиспам).** Для каждого соединения хранится очередь моментов последних сообщений.
> При новом сообщении из начала очереди выбрасываются все, что старше секунды; если осталось 5 — это шестое за
> секунду, отказ. Как турникет, который пропускает не больше пяти человек в секунду. `deque` («дек») — очередь, из
> которой быстро удалять с начала (обычный список Python при этом сдвигал бы все элементы).

Затем: время `ЧЧ:ММ` от клиента проверяется `TIME_RE`, при неверном формате подставляется время сервера; сообщение
записывается в `messages`; `emit("message", msg, broadcast=True)` рассылает его **всем, включая отправителя**.

**`on_typing()`** — «печатает…»: если соединение вошло, разослать `{nickname}` всем, кроме него самого.

**`on_disconnect(*args)`** — отключение (закрыли вкладку, пропала сеть):

```python
with lock:
    login = online.pop(request.sid, None)          # убрать соединение из «в сети»
    recent.pop(request.sid, None)                  # и его антиспам-очередь
    still_online = login in online.values()        # не осталось ли у человека другой вкладки?
    users = users_online()
if login:
    if not still_online:
        emit("system", {"text": f"{login} вышел из сети"}, broadcast=True)   # объявляем, только если ушёл совсем
    emit("users", users, broadcast=True)
```

`*args` в объявлении — «принять сколько угодно аргументов»: разные версии Flask-SocketIO передают в обработчик
отключения разное число параметров, а так функция совместима с любой.

### 2.8. Обычные HTTP-маршруты

- **`index`** (`GET /`) — отдаёт страницу веб-клиента: `render_template_string(WEB_CLIENT)`. Шаблон берётся из
  строки; автоэкранирование Jinja включено и для таких шаблонов.
- **`health`** (`GET /health`) — «проверка пульса»: `{"ok": true, "online": 3}`. Такие адреса используют системы
  мониторинга, чтобы убедиться, что сервер жив. Flask сам превращает возвращённый словарь в JSON.

### 2.9. Запуск

```python
init_db()                                              # таблицы создаются при любом подключении модуля (и в тестах)

if __name__ == "__main__":                             # только при прямом запуске python server.py
    socketio.run(app, host=os.environ.get("ICQ_HOST", "0.0.0.0"), port=PORT, allow_unsafe_werkzeug=True)
```

- `socketio.run` вместо `app.run` — запуск сервера, умеющего и HTTP, и Socket.IO.
- `host="0.0.0.0"` — слушать **на всех сетевых интерфейсах**: к серверу можно подключиться не только с этого
  компьютера, но и из локальной сети по его IP-адресу (так одногруппники могут зайти на ваш сервер). В CRM, наоборот,
  `127.0.0.1` — только локально. Брандмауэр Windows при первом запуске может спросить разрешение.
- `allow_unsafe_werkzeug=True` — явное согласие использовать встроенный учебный веб-сервер Werkzeug. Библиотека по
  умолчанию отказывается запускать его «как боевой»: он не рассчитан на нагрузку и интернет. Для занятий и локальной
  сети — подходит.

## 3. server.py: веб-клиент `WEB_CLIENT`

Весь веб-клиент — одна HTML-страница в строке `WEB_CLIENT = r"""…"""`. Буква `r` перед кавычками делает строку
«сырой»: обратная косая черта `\` в JavaScript не требует удвоения (в CRM строки обычные, и там приходится писать
`\\n`).

### 3.1. Разметка (HTML)

Два «окна» в стиле старой ICQ:

- `<div id="login">` — окно входа: цветок, форма `loginForm` (поля `lg` — логин, `pw` — пароль типа `password`, то
  есть со скрытыми символами), строка ошибки `err`, подсказка «Первый вход с новым ником — регистрация. Пароль
  хранится на сервере только в виде хеша».
- `<div id="app">` — окно чата, скрытое до входа: слева список «В сети» (`users`) с кнопками «Звук» и «Выйти»,
  справа — лента сообщений (`messages`), строка «печатает…» (`typing`), панель смайлов (`smiles`) и форма отправки
  (`sendForm`).

Атрибуты `maxlength="20"`, `maxlength="64"`, `maxlength="1000"` повторяют серверные ограничения — подсказка
пользователю. Но настоящая проверка — на сервере: браузерные ограничения легко обойти.

### 3.2. Оформление (CSS)

- **CSS-переменные** в `:root` (`--green`, `--bg`, `--line`, …) — цвета заданы один раз и используются везде.
- **Цветок ICQ нарисован без картинок**: семь элементов `<i>` (лепестков) одинаковой формы, каждый повёрнут на
  ~51° (360° / 7) вокруг общей точки (`transform-origin`), первый — красный, в центре жёлтый круг `<b>`. Большой цветок
  в окне входа — тот же, увеличенный `transform: scale(2.2)`.
- Свои сообщения (`.msg.mine`) — справа и в зелёном «пузыре», чужие — слева в белом. Скругление углов пузыря
  разное (`border-radius: 4px 14px 14px 14px`), чтобы получился «хвостик» к автору.
- `white-space: pre-wrap; word-wrap: break-word` — переводы строк в сообщении сохраняются, длинные слова переносятся.
- `@media (max-width: 760px)` — на телефоне список «В сети» уходит над чатом (адаптивная вёрстка).

### 3.3. Поведение (JavaScript)

**Помощники:**

```javascript
const $ = id => document.getElementById(id);           // короткое имя для «найди элемент по id»
const ROOT = {{ request.script_root|tojson }};          // префикс адреса, если сервер смонтирован не в корне
let socket = null, me = null, soundOn = true, typingTimer = null, lastTyping = 0;   // состояние клиента

function esc(s) { const d = document.createElement('div'); d.textContent = s; return d.innerHTML; }  // экранирование
function hhmm() { const d = new Date(); return String(d.getHours()).padStart(2, '0') + ':' + String(d.getMinutes()).padStart(2, '0'); }
```

> **Понятие. DOM и события.** Браузер превращает HTML в дерево объектов (DOM), а JavaScript находит в нём элементы и
> меняет их. «Событие» — сигнал о действии (отправка формы, ввод символа, клик); `addEventListener('submit', функция)`
> — подписка: «когда случится — выполни».

**`addMessage(m, silent)`** — показать сообщение:

```javascript
div.className = 'msg' + (m.nickname === me ? ' mine' : '');       // своё — с классом mine (справа, зелёное)
div.innerHTML = `<div class="who">${esc(m.nickname)}<span class="t">${esc(m.time || '')}</span></div><div class="bubble">${esc(m.text)}</div>`;
//              ↑ ВСЕ данные от сервера (ник, время, текст) вставляются только через esc()
box.appendChild(div); box.scrollTop = box.scrollHeight;           // добавить и прокрутить вниз
if (!silent && m.nickname !== me) {                               // чужое и не из истории:
    uhOh();                                                       //   звук «о-оу»
    if (document.hidden) document.title = '✉ ' + m.nickname + ' — ICQ';   //   вкладка в фоне — мигнуть заголовком
}
```

> **Понятие. XSS.** Если кто-то пришлёт сообщение `<img src=x onerror="…вредный код…">`, а клиент вставит его
> в `innerHTML` как есть, код выполнится у **всех** участников чата. Функция `esc()` превращает `<` в `&lt;` и т. п.,
> и браузер покажет текст, а не выполнит его. В мессенджере, где текст приходит от посторонних людей, это критично.
> Системные сообщения (`addSystem`) вставляются через `textContent` — он безопасен сам по себе.

Событие `visibilitychange` возвращает обычный заголовок вкладки, когда пользователь на неё вернулся.

**Вход** — обработчик отправки формы `loginForm`:

```javascript
socket = io({path: ROOT + '/socket.io'});                           // подключиться к Socket.IO этого же сервера
socket.on('connect', () => socket.emit('join', {login, password})); // соединение есть — отправить join
socket.on('connect_error', () => showLogin('Сервер недоступен'));
socket.on('history', list => { … });                                // пришла история = вход успешен: показать чат
socket.on('message', m => addMessage(m));
socket.on('system', m => addSystem(m.text));
socket.on('error', m => { … });
socket.on('users', list => { … });                                  // перерисовать список «В сети»
socket.on('typing', m => { … });
socket.on('disconnect', () => { if (me) addSystem('Связь потеряна — переподключаемся…'); });
```

Особенности:

- **Признак успешного входа** — приход события `history`: только тогда окно входа прячется и показывается чат.
  Логин запоминается в `localStorage` (хранилище браузера), при следующем открытии поле логина заполнено.
  Пароль никуда не сохраняется, поле пароля очищается.
- **Автопереподключение.** Браузерная библиотека socket.io-client при обрыве связи сама пытается переподключиться,
  а при успехе снова срабатывает `connect` — и клиент **автоматически повторяет `join`**. Пользователь видит
  «Связь потеряна — переподключаемся…», а затем снова историю.
- **Разбор ошибок** — единственное место с регулярным выражением в JS:

```javascript
socket.on('error', m => {
    if (me && $('app').classList.contains('on') && !/пароль|войдите|вход/i.test(m.text)) {
        addSystem('⚠ ' + m.text);          // уже в чате и ошибка «рабочая» (спам, длинное сообщение) — показать в ленте
    } else {
        me = null; showLogin(m.text);      // ошибка входа — вернуться на экран входа (правило протокола)
    }
});
```

`/пароль|войдите|вход/i` — «встречается ли в тексте “пароль”, “войдите” или “вход”, без учёта регистра». Так
предупреждение о спаме не выкидывает пользователя из чата, а ошибка авторизации — выкидывает.

- **`showLogin(error)`** прячет чат, показывает окно входа с текстом ошибки и полностью закрывает соединение:
  `socket.off()` снимает все подписки, `socket.disconnect()` рвёт связь.

**Отправка и «печатает…»:**

```javascript
$('sendForm').addEventListener('submit', e => {
    e.preventDefault();                                       // не перезагружать страницу
    const text = $('text').value.trim();
    if (!text || !socket) return;
    socket.emit('message', {text, time: hhmm()});             // время «ЧЧ:ММ» по часам клиента, как в протоколе
    $('text').value = '';
});
$('text').addEventListener('input', () => {                   // при каждом вводе символа…
    if (socket && Date.now() - lastTyping > 1500) {           // …но не чаще раза в 1,5 секунды
        socket.emit('typing'); lastTyping = Date.now();
    }
});
```

Ограничение «не чаще раза в 1,5 с» (**throttling**, «дросселирование») не даёт засыпать сервер событием на каждое
нажатие клавиши. На стороне получателя надпись «X печатает…» живёт 2 секунды: каждый новый сигнал перезапускает
таймер (`clearTimeout` + `setTimeout`), и надпись исчезает через 2 с после последнего сигнала.

Остальное: кнопка «Выйти» (`showLogin('')`), переключатель звука, панель смайлов (кнопки создаются в цикле; клик
дописывает смайл в поле ввода).

### 3.4. Синтез звука «о-оу» в браузере: `uhOh`

Звуковой файл не нужен — звук **синтезируется** на лету через WebAudio API.

> **Понятие. Как синтезируется звук.** Звук — колебания давления воздуха. Высота тона — частота колебаний в герцах
> (Гц): 880 Гц — нота «ля» второй октавы, 587 Гц — «ре» второй октавы. **Осциллятор** — генератор колебаний заданной
> формы и частоты. **Огибающая** громкости — как громкость меняется во времени: быстро нарастает (атака) и затухает
> (спад). Без огибающей резкое включение и выключение звука слышно как щелчок.

```javascript
const ctx = new (window.AudioContext || window.webkitAudioContext)();   // «звуковая студия» браузера
[[880, 0], [587, .16]].forEach(([freq, at]) => {                         // две ноты: 880 Гц сразу, 587 Гц через 0,16 с
    const o = ctx.createOscillator(), g = ctx.createGain();              // генератор тона и регулятор громкости
    o.type = 'triangle'; o.frequency.value = freq;                       // треугольная волна — мягче «пищалки»
    g.gain.setValueAtTime(.0001, ctx.currentTime + at);                  // начать почти с тишины
    g.gain.exponentialRampToValueAtTime(.25, ctx.currentTime + at + .02);    // за 20 мс — до четверти громкости
    g.gain.exponentialRampToValueAtTime(.0001, ctx.currentTime + at + .15);  // к 150 мс — затухание
    o.connect(g).connect(ctx.destination);                               // генератор → громкость → динамики
    o.start(ctx.currentTime + at); o.stop(ctx.currentTime + at + .16);
});
```

Нисходящая пара «высокая — пониже» и даёт узнаваемое «о-оу». Экспоненциальное изменение громкости
(`exponentialRamp…`) звучит естественнее линейного — так воспринимает громкость человеческое ухо; поэтому и
начальная громкость не 0, а 0,0001 (экспонента не может начинаться с нуля). Весь код обёрнут в `try { … } catch`,
чтобы отсутствие звука не ломало чат.

## 4. client_desktop.py: настольный клиент

### 4.1. Описание модуля и настройки

Docstring перечисляет **семь правил общего сервера группы** и то, как клиент их выполняет — по сути, это
требования к клиенту, записанные как чек-лист: связь через python-socketio; адрес сервера вводится в окне входа и
запоминается; вход — `join`; отправка — `message {text, time}`; приём `message / system / history / error`
(+ `users`, `typing`); минимальный интерфейс; при `error` — показать текст и вернуться ко входу.

Константы: `CONFIG_FILE` (`icq_client.json` рядом с программой), `DEFAULT_SERVER = "http://127.0.0.1:5055"`,
`SMILES` — набор смайлов.

> **Понятие. Tkinter.** Библиотека для оконных программ, встроенная в Python. Окно состоит из **виджетов**: надписей
> (`Label`), полей ввода (`Entry`), кнопок (`Button`), списков (`Listbox`), многострочного текста (`Text`). `ttk` —
> более современные на вид версии виджетов с поддержкой стилей.

### 4.2. `IcqConnection` — сеть отдельно от интерфейса

Класс отвечает только за связь с сервером и **ничего не знает об окнах**. Это сделано намеренно: сетевую часть можно
проверить автотестом без открытия окон (так и сделано в `test_desktop_client_over_network`).

```python
class IcqConnection:
    def __init__(self):
        self.events = queue.Queue()                        # очередь входящих событий: (тип, данные)
        self.sio = socketio.Client(reconnection=False, logger=False, engineio_logger=False)
        for name in ("message", "system", "history", "error", "users", "typing"):
            self.sio.on(name, self._make_handler(name))    # на каждое событие — обработчик «положить в очередь»
        self.sio.on("disconnect", lambda *a: self.events.put(("disconnect", None)))

    def _make_handler(self, name):
        return lambda data=None: self.events.put((name, data))   # обработчик «помнит» своё имя события

    def connect(self, server, login, password, timeout=10):
        self.sio.connect(server, transports=["polling", "websocket"], wait_timeout=timeout)
        self.sio.emit("join", {"login": login, "password": password})
```

- **Все события складываются в очередь**, а не обрабатываются сразу. Почему — в разделе 4.3.
- `_make_handler(name)` — «фабрика» обработчиков. Если бы написать прямо в цикле
  `lambda data: self.events.put((name, data))`, все шесть обработчиков «видели» бы одно и то же, последнее значение
  `name` (`"typing"`) — классическая ловушка Python: функция запоминает не значение переменной, а саму переменную.
  Вызов отдельной функции фиксирует значение для каждого обработчика.
- `data=None` — значение по умолчанию: некоторые события приходят без данных.
- `reconnection=False` — не переподключаться автоматически: при обрыве клиент возвращается к окну входа (так проще
  и честнее для пользователя).
- `send(text)` отправляет `message` с текущим временем `ЧЧ:ММ`; `typing()` и `close()` проверяют, что соединение
  живо (`self.sio.connected`).

### 4.3. Потоки в настольном клиенте: почему нужна очередь

В работающем клиенте одновременно действуют несколько потоков:

```
 Главный поток (Tkinter)                     Фоновые потоки
 ─────────────────────────                   ──────────────────────────────────────────────────────────
 mainloop(): рисует окно,                    worker (do_login): подключение к серверу — может длиться
 обрабатывает клики и клавиши                до 10 секунд; в главном потоке окно бы «зависло»
        ▲
        │ каждые 100 мс poll():              поток python-socketio: принимает события от сервера
        │ забрать всё из очереди             и вызывает обработчики → events.put((тип, данные))
        │ и обработать в handle()                       │
        └────────────── queue.Queue ◄───────────────────┘
                                             поток звука: winsound.PlaySound (не блокирует окно)
```

> **Понятие. Почему Tkinter нельзя трогать из другого потока.** Tkinter, как и большинство оконных библиотек,
> **не потокобезопасен**: окно должен менять только тот поток, который его создал (главный). Если фоновый поток
> python-socketio, получив сообщение, сам полезет дописывать текст в окно в тот момент, когда главный поток его
> перерисовывает, результат непредсказуем: от «битого» окна до падения программы. Аналогия: в зале суда протокол
> ведёт один секретарь; остальные участники не пишут в протокол сами, а передают ему записки.

**Решение — очередь + таймер `after`:**

1. Фоновые потоки только **кладут записки** в `queue.Queue` — эта очередь как раз потокобезопасна (внутри у неё
   свой замок).
2. Главный поток каждые 100 мс забирает записки и сам меняет окно:

```python
def poll(self):
    while self.conn:                                     # пока есть соединение
        try:
            kind, data = self.conn.events.get_nowait()   # взять событие, НЕ дожидаясь (если пусто — исключение)
        except queue.Empty:
            break                                        # очередь пуста — хватит
        self.handle(kind, data)                          # обработать в главном потоке
    self.after(100, self.poll)                           # попросить Tkinter вызвать poll снова через 100 мс
```

`after(мс, функция)` — «напомни через столько-то миллисекунд» внутри главного цикла Tkinter. `get_nowait()` не
ждёт: главный поток не должен блокироваться, иначе окно перестанет отвечать. 100 мс — задержка, которую человек не
замечает.

Та же схема используется при входе: `do_login` запускает подключение в отдельном потоке `worker`, а при ошибке
этот поток не показывает окно ошибки сам, а кладёт в очередь `("connect_failed", текст)`.

`daemon=True` у фоновых потоков — «служебный» поток: он не мешает программе завершиться, когда закрыто главное окно.

### 4.4. Звук «о-оу»: `make_uh_oh_wav`, `play_uh_oh`

В настольном клиенте звук тоже синтезируется, но «вручную» — как массив чисел, из которого собирается WAV-файл
в памяти.

> **Понятие. Цифровой звук.** Микрофон и динамик работают с непрерывной волной, а компьютер хранит её как
> **отсчёты** — значения громкости через равные промежутки времени. **Частота дискретизации** 22 050 Гц — 22 050
> отсчётов в секунду. **Разрядность** 16 бит — каждый отсчёт — целое число от −32 768 до 32 767. WAV — простой формат:
> заголовок (сколько каналов, какая частота, какая разрядность) и за ним подряд все отсчёты.

```python
rate, frames = 22050, bytearray()                     # 22 050 отсчётов в секунду; пустой массив байтов
for freq, dur in ((880, 0.14), (587, 0.18)):          # две ноты: 880 Гц 0,14 с и 587 Гц 0,18 с
    n = int(rate * dur)                               # сколько отсчётов в ноте (3087 и 3969)
    for i in range(n):
        envelope = min(1, i / 300) * min(1, (n - i) / 900)   # огибающая: нарастание ~14 мс, затухание ~41 мс
        frames += struct.pack("<h", int(9000 * envelope * math.sin(2 * math.pi * freq * i / rate)))
        #          ↑ синусоида заданной частоты × огибающая × 9000 → целое → 2 байта (16 бит, младший байт первым)
buf = io.BytesIO()                                    # «файл» в оперативной памяти
with wave.open(buf, "wb") as w:
    w.setnchannels(1)                                 # моно
    w.setsampwidth(2)                                 # 2 байта на отсчёт
    w.setframerate(rate)                              # 22 050 отсчётов в секунду
    w.writeframes(bytes(frames))                      # модуль wave сам допишет заголовок RIFF/WAVE
return buf.getvalue()
```

- Формула `sin(2π · f · i / rate)` даёт значение синусоиды частотой `f` в момент `i / rate` секунд.
- Амплитуда 9000 из максимальных 32 767 — примерно четверть громкости, чтобы не оглушать.
- `struct.pack("<h", …)`: `h` — короткое целое со знаком (2 байта), `<` — порядок байтов «младший первым»
  (little-endian), как требует WAV.
- Итог — около 14 КБ: 7056 отсчётов × 2 байта + 44 байта заголовка. Тест проверяет, что файл начинается с `RIFF` и
  содержит `WAVE`.

```python
def play_uh_oh(root):
    try:
        import winsound                                   # модуль есть только в Windows
        data = make_uh_oh_wav()
        threading.Thread(target=winsound.PlaySound, args=(data, winsound.SND_MEMORY), daemon=True).start()
    except Exception:
        root.bell()                                       # не Windows — системный «бип»
```

`winsound.PlaySound` с флагом `SND_MEMORY` играет звук из памяти, но **ждёт окончания** звучания. Поэтому он
запускается в отдельном потоке — иначе окно «замирало» бы на треть секунды при каждом сообщении.

| | Веб-клиент | Настольный клиент |
|---|---|---|
| Технология | WebAudio: осциллятор + регулятор громкости | Ручной расчёт отсчётов → WAV в памяти → `winsound` |
| Форма волны | Треугольная | Синусоида |
| Ноты | 880 Гц, затем 587 Гц через 0,16 с | 880 Гц 0,14 с, затем 587 Гц 0,18 с |
| Огибающая | Экспоненциальная: 20 мс нарастание, затухание к 150 мс | Линейная: ~14 мс нарастание, ~41 мс затухание |

### 4.5. Окно: класс `App(tk.Tk)`

`App` **наследует** `tk.Tk` — главное окно Tkinter: получает всё поведение окна и добавляет своё.

**`__init__`** — заголовок, размер, цвета; `tk.BooleanVar` для галочки «звук» (особая переменная, связанная с
виджетом: галочка и переменная всегда в одном состоянии); загрузка настроек; стиль кнопок `Green.TButton` на теме
`clam`; показ окна входа; запуск цикла `poll` (`self.after(100, self.poll)`); `protocol("WM_DELETE_WINDOW",
self.on_close)` — перехват нажатия на крестик, чтобы сначала корректно закрыть соединение.

**`load_config` / `save_config`** — чтение и запись `icq_client.json` (`{"server": …, "login": …}`). Ошибки чтения
(файла нет, файл испорчен) не страшны — берутся значения по умолчанию. **Пароль в файл не пишется** — осознанное
требование из docstring.

**`clear`** — удалить текущее содержимое окна и создать пустую рамку (`Frame`). Так одно окно переключается между
«экраном входа» и «экраном чата».

**`show_login(error="")`** — экран входа: цветок, надпись ICQ, три поля (адрес сервера, логин, пароль). Поля
связаны с `StringVar` — переменными, из которых удобно читать введённый текст (`self.v_login.get()`). У поля пароля
`show="•"` — символы скрыты. `bind("<Return>", …)` — Enter в любом поле запускает вход.

**`do_login`** — проверяет, что все поля заполнены; дописывает `http://`, если адрес указан без схемы; показывает
«Подключение…» (`update_idletasks()` — перерисовать окно немедленно, до начала долгой операции); сохраняет адрес и
логин; создаёт `IcqConnection` и запускает подключение в фоновом потоке. Логин запоминается в `pending_login` —
«ожидающий подтверждения»: пользователь ещё не вошёл, пока сервер не ответил.

**`show_chat`** — экран чата:

- зелёная верхняя полоса «ICQ — логин», галочка «звук», кнопка «Выйти»;
- `PanedWindow` — две панели с перетаскиваемой границей: слева список «В сети» (`Listbox`), справа лента;
- лента — виджет `Text` с полосой прокрутки и **тегами оформления**: `who` (синий жирный ник), `me` (зелёный
  жирный — свой ник), `time` (серое мелкое время), `sys` (серый курсив по центру — системные сообщения);
- строка «печатает…», панель смайлов, поле ввода и кнопка «Отправить». Enter — отправить; любое нажатие клавиши
  (`<Key>`) — сигнал `typing`.

В цикле создания кнопок смайлов — приём `command=lambda s=s: …`: значение по умолчанию `s=s` «замораживает» текущий
смайл для каждой кнопки (та же ловушка, что и в `_make_handler`).

**`write(*parts)`** — дописать в ленту кусочки текста с тегами. Лента обычно в состоянии `disabled` (пользователь
не может в ней печатать); на время записи она включается и сразу выключается обратно, затем `see("end")` прокручивает
вниз.

**`add_message(m, silent=False)`** — ник (своим или чужим цветом), время, текст; звук — только для чужих сообщений,
не из истории и при включённой галочке.

**`send`**, **`logout`**, **`on_close`** — отправить текст и очистить поле; закрыть соединение и вернуться ко входу;
закрыть соединение и окно.

### 4.6. Обработка событий: `handle(kind, data)`

`handle` — диспетчер: по типу события выбирает реакцию. Всё выполняется в главном потоке (вызов из `poll`).

| Событие | Реакция |
|---|---|
| `connect_failed` | Сервер недоступен: соединение сбрасывается, экран входа с текстом ошибки |
| `history` | Если ещё не вошли — это знак успешного входа: `me = pending_login`, показать чат. Вывести историю без звука, затем «— конец истории —» |
| `message` | Если ещё не вошли (сервер без `history`) — тоже считать вход выполненным. Показать сообщение со звуком |
| `system` | Если ещё не вошли — первое системное сообщение = вход выполнен. Вывести серым курсивом |
| `users` | Перерисовать список «В сети», себя отметить «(вы)» |
| `typing` | Показать «X печатает…», через 2 с очистить (`after(2000, …)`) |
| `error` | Если уже в чате и в тексте есть «спам» — показать предупреждение в ленте и остаться. Иначе закрыть соединение, показать окно ошибки (`messagebox.showerror`) и вернуться ко входу — правило №7 протокола |
| `disconnect` | Если были в чате — экран входа «Соединение с сервером потеряно» |

Несколько способов «понять, что вход удался» (`history`, `message` или `system`) — **устойчивость к чужим серверам**:
клиент рассчитан на подключение не только к своему серверу, но и к общему серверу группы, который может вести себя
немного иначе.

| Угроза | Защита в коде | Где |
|---|---|---|
| Утечка паролей из базы | Хранится только хеш с солью (scrypt в Werkzeug 3.x) | `check_user`, `generate_password_hash` |
| Подбор пароля | 5 неверных попыток подряд → блокировка логина на 15 минут | `on_join`, словари `wrong`, `banned` |
| Спам и флуд | Не больше 5 сообщений в секунду с соединения | `on_message`, словарь `recent` |
| Мусор в данных | Логин по шаблону 2–20 символов, пароль 1–64, текст до 1000, время в формате `ЧЧ:ММ`, проверка типа данных (`isinstance(data, dict)`) | `LOGIN_RE`, `TIME_RE`, `MAX_TEXT` |
| Сообщения без входа | `message` принимается только от соединения, выполнившего `join` | `on_message` |
| SQL-инъекции | Только параметры `?` | все запросы |
| XSS в веб-клиенте | Экранирование `esc()` и `textContent` | `addMessage`, `addSystem`, список пользователей |
| Гонки между потоками | Общие словари меняются только под `lock` | `on_join`, `on_message`, `on_disconnect` |
| Хранение пароля на клиенте | Пароль не сохраняется ни в `icq_client.json`, ни в `localStorage` | `save_config`, веб-клиент |

Чего **нет** (подробнее в разделе 9): шифрования канала (HTTPS/WSS) при запуске «как есть», ограничения источников
подключения (`cors_allowed_origins="*"`), защиты от блокировки чужого логина.

## 8. Проверь себя

<details>
<summary>1. Почему для чата не подходит обычная схема HTTP «запрос — ответ»?</summary>

В HTTP сервер отвечает только на запрос клиента и не может сам сообщить о новом сообщении. Пришлось бы постоянно
опрашивать сервер. WebSocket держит постоянное двустороннее соединение, и сервер отправляет сообщение, как только
оно появилось.
</details>

<details>
<summary>2. Чем long polling отличается от WebSocket и зачем Socket.IO использует оба?</summary>

Long polling — серия HTTP-запросов, каждый из которых сервер держит открытым до появления новости. WebSocket — одно
постоянное соединение без повторных заголовков. Socket.IO начинает с long polling (работает везде) и переходит на
WebSocket, если это возможно, — так связь есть даже в сетях, где WebSocket блокируется.
</details>

<details>
<summary>3. Что означают <code>broadcast=True</code> и <code>include_self=False</code> в строке «Сергей в сети»?</summary>

Разослать событие всем подключённым, кроме самого Сергея: ему уходит своё приветствие «С возвращением», а остальным —
уведомление о его появлении.
</details>

<details>
<summary>4. Почему отправитель видит своё сообщение, хотя клиент не добавляет его в ленту при отправке?</summary>

Сервер рассылает сообщение всем, включая отправителя (`broadcast=True` без `include_self=False`). Так все видят
сообщения в одном порядке, а отправитель получает подтверждение, что сервер сообщение принял.
</details>

<details>
<summary>5. Зачем хранить хеш пароля, а не сам пароль? Что такое соль?</summary>

При утечке базы хеш не позволяет узнать пароль: по хешу пароль не восстановить, а медленный алгоритм делает перебор
очень долгим. Соль — случайная добавка, уникальная для каждого пользователя: одинаковые пароли дают разные хеши,
и заранее посчитанные таблицы хешей бесполезны.
</details>

<details>
<summary>6. Пользователь 5 раз ввёл неверный пароль, а потом верный. Что произойдёт?</summary>

После пятой ошибки логин блокируется на 15 минут (`banned`). Проверка бана идёт **до** проверки пароля, поэтому даже
верный пароль получит ответ «вход закрыт до ЧЧ:ММ». Это проверяется тестом `test_errors_and_protection`.
</details>

<details>
<summary>7. Как работает антиспам «не больше 5 сообщений в секунду»?</summary>

Для каждого соединения хранится очередь `deque` моментов отправки. При новом сообщении из начала очереди удаляются
записи старше одной секунды; если осталось 5 — сообщение отклоняется с ошибкой, иначе момент добавляется в очередь.
Это «скользящее окно».
</details>

<details>
<summary>8. Зачем серверу <code>threading.Lock</code>?</summary>

В режиме `threading` клиенты обслуживаются параллельными потоками, которые меняют общие словари (`online`, `wrong`,
`banned`, `recent`). Без замка возможны гонки: например, два потока одновременно увеличат счётчик неверных паролей и
одна попытка «потеряется». Замок пускает к словарям только один поток за раз.
</details>

<details>
<summary>9. Почему настольный клиент не меняет окно прямо в обработчике события от сервера?</summary>

Обработчики python-socketio выполняются в фоновом потоке, а Tkinter можно трогать только из главного потока. Поэтому
фоновый поток кладёт событие в `queue.Queue`, а главный поток каждые 100 мс забирает события (`after` + `poll`) и сам
обновляет окно.
</details>

<details>
<summary>10. Что сломалось бы, если в цикле написать <code>self.sio.on(name, lambda data: self.events.put((name, data)))</code>?</summary>

Все обработчики ссылались бы на одну и ту же переменную `name`, которая после цикла равна последнему значению
(`"typing"`). Любое событие попадало бы в очередь как `typing`. `_make_handler(name)` фиксирует своё значение для
каждого обработчика.
</details>

<details>
<summary>11. Как из чисел получается звук «о-оу» в настольном клиенте?</summary>

Для каждой ноты (880 Гц, затем 587 Гц) вычисляются 22 050 отсчётов в секунду по формуле синусоиды, умноженной на
огибающую (плавное нарастание и затухание против щелчков). Отсчёты упаковываются в 16-битные числа, модуль `wave`
добавляет заголовок — получается WAV в памяти, который проигрывает `winsound` в отдельном потоке.
</details>

<details>
<summary>12. Почему при закрытии одной из двух вкладок пользователя остальные не видят «вышел из сети»?</summary>

`on_disconnect` проверяет `still_online = login in online.values()`: если у логина осталось другое соединение,
уведомление о выходе не рассылается, обновляется только список `users`.
</details>

<details>
<summary>13. Чем <code>host="0.0.0.0"</code> в ICQ отличается от <code>127.0.0.1</code> в CRM?</summary>

`127.0.0.1` — сервер доступен только с этого компьютера. `0.0.0.0` — сервер слушает все сетевые интерфейсы, и к нему
можно подключиться с других компьютеров локальной сети по IP-адресу — это нужно, чтобы одногруппники зашли на ваш
сервер.
</details>

## 9. Что можно улучшить дальше

**Безопасность**

- **Нет шифрования канала.** При запуске «как есть» соединение идёт по `http://` / `ws://`, и пароль при входе
  передаётся по сети открытым текстом. В интернете нужен HTTPS/WSS (сертификат TLS) — хеширование защищает базу,
  но не сам канал.
- **Бан по логину позволяет «заблокировать» чужой аккаунт**: злоумышленник пять раз вводит неверный пароль к чужому
  нику — и настоящий владелец 15 минут не может войти. Лучше учитывать и IP-адрес, добавлять нарастающую задержку
  или капчу.
- **Регистрация при первом входе**: опечатка в нике молча создаёт новый аккаунт; нет смены и восстановления пароля,
  нет требований к сложности пароля (достаточно одного символа).
- **`cors_allowed_origins="*"`** — подключаться можно со страниц любых сайтов; для публичного сервера стоит указать
  список разрешённых адресов.
- Время сообщения берётся от клиента (проверяется только формат) — можно прислать любое «ЧЧ:ММ». Серверное время
  (`ts`) сохраняется, но клиентам не отправляется.

**Архитектура и масштаб**

- **Состояние в памяти** (`online`, `banned`, `recent`) теряется при перезапуске и не работает, если запустить
  несколько процессов сервера. Для масштабирования Flask-SocketIO использует внешнюю очередь сообщений (например,
  Redis).
- **Учебный веб-сервер** (`allow_unsafe_werkzeug=True`, режим `threading`) не рассчитан на нагрузку; для реальной
  эксплуатации — eventlet/gevent или отдельный сервер.
- `with db_connect() as db` в модуле `sqlite3` фиксирует транзакцию, но **не закрывает** соединение — его закрывает
  сборщик мусора. Надёжнее закрывать явно (`contextlib.closing`).
- Один общий чат: нет личных сообщений, комнат, статусов «отошёл / не беспокоить», редактирования и удаления сообщений,
  отметок «доставлено / прочитано».
- История — только 50 последних сообщений, без подгрузки более ранних и без поиска.
- ICQ пока не подключён к сайту портфолио.

**Клиенты**

- Настольный клиент не переподключается автоматически (`reconnection=False`) — при обрыве связи нужно войти заново.
- Настольный клиент отправляет `typing` на **каждое** нажатие клавиши (в веб-клиенте — не чаще раза в 1,5 с);
  стоит добавить такое же ограничение.
- WAV-звук генерируется заново при каждом сообщении — его можно вычислить один раз и хранить.
- Надпись «печатает…» в настольном клиенте очищается через 2 с после **первого** сигнала, даже если человек ещё
  печатает (таймеры `after` не отменяются); в веб-клиенте это сделано правильно через `clearTimeout`.
- Веб-клиент создаёт новый `AudioContext` на каждый звук; браузеры ограничивают число таких объектов — лучше
  создать один и переиспользовать.
- Интерфейс веб-клиента не покрыт автотестами (тестируются сервер, сетевой клиент и звук).
